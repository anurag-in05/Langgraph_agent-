Architecture

The project is a Python chat app for workout suggestions, meal planning, and general mental wellness tips. LangGraph coordinates the work, LangChain supplies model and tool interfaces, and Streamlit renders the conversation.

Each role uses the same configured model. The roles differ in prompts, available tools, and responsibility. The current app uses llama-3.3-70b-versatile through ChatGroq. The prototype notebook and the older app commit 5a887fd use qwen2.5:14b through ChatOllama. For a demo, name the model in the version you are actually running.

Trace a request

These are illustrative paths through the graph. Routing, tool use, and wording depend on the model's decisions.

“Can you suggest a vegetarian meal plan for today?”

  1. main.py converts the input to a HumanMessage and calls graph.stream with the session's thread ID.
  2. The supervisor can produce {"next": "dietitian"}. A LangGraph Command transfers control to that worker.
  3. The worker's ReAct agent can call diet_tool(query="vegetarian"). The tool requests a daily plan and then fetches details for each returned recipe.
  4. The worker appends its final text as an AIMessage named dietitian. The UI displays it from the graph update.
  5. The supervisor sees the reply prefixed with dietitian and can return FINISH, which maps to END.

“Give me a lower-body workout.”

  1. The supervisor can choose fitness after seeing the chat message.
  2. The worker can call fitness_data_tool(query="lower_body"). The tool chooses one muscle in that category and one exercise type at random.
  3. API Ninjas receives those filters and the default intermediate difficulty. The tool formats up to three records with names, muscles, and instructions.
  4. The fitness agent can use the returned records in its answer. The worker emits the reply, and control returns to the supervisor.

“Can you share a simple way to unwind before bed?”

  1. The supervisor can route to the wellness node.
  2. wellness_node sends a system message followed by the conversation history.
  3. The shared model generates a tip without calling an exercise or meal API. The worker adds its reply and returns to the supervisor.

“Suggest a workout and a vegan meal plan.”

  1. The supervisor picks one worker per decision. One possible route is supervisor → fitness → supervisor → dietitian → supervisor → END.
  2. The UI renders each worker's reply when that node finishes. The messages remain available to the supervisor and later workers on the same thread.
  3. The model can also choose a different order, repeat a worker, or finish early. The current state tracks messages and the next route. It has no explicit checklist of requested topics.

Supervisor and workers

The outer loop routes between specialists

A graph node is a function that receives shared state. State extends MessagesState, which keeps a growing conversation as nodes add messages. The extra next field records the supervisor's destination. The goto on the returned Command controls where the graph actually goes.

class State(MessagesState):
    next: str

class Router(TypedDict):
    next: Route

The supervisor prepends its system prompt to the messages and uses model.with_structured_output(Router, method="function_calling"). The schema supplies four possible values for next. The node validates the value, translates FINISH to END, and returns the route and state update together.

main.py registers the four nodes and adds the explicit edge from START to supervisor. Node commands handle the remaining transitions at runtime.

The inner loops let fitness and dietitian use tools

ReAct combines reasoning and acting. LangChain's create_agent builds each worker's tool-calling loop. The model can call its registered tool, read the returned data, and decide whether to use the tool again or answer. Each worker has one tool and a short domain prompt.

result = fitness_agent.invoke({"messages": state["messages"]})
return _specialist_reply("fitness", result["messages"][-1].text)

The worker publishes the final message content to the outer graph. Internal tool calls and raw tool responses stay inside the worker invocation. The dietitian follows the same wrapper pattern.

The wellness worker is a direct model call

wellness_node sends a system message and the chat history directly to the shared model. It adds a wellness reply and returns to the supervisor. The conversation lets it tailor the tip to what the user shared.

External API tools

The @tool wrappers give the model a callable name, a description from the docstring, and a string argument with guidance from Annotated. The wrapper creates a client object and calls its plan method. The client owns the HTTP request and formats the response as a list of strings. The category descriptions guide the model. The code uses a plain str argument.

FitnessData and API Ninjas

  1. fitness_data_tool(query) forwards the category to generate_workout_plan. The expected categories are full_body, upper_body, and lower_body. Unknown categories fall back to full_body.
  2. The planner chooses a muscle from MUSCLE_GROUPS and an exercise type from EXERCISE_TYPES. The tool uses the planner's default intermediate difficulty.
  3. fetch_exercises calls /v1/exercises with type, muscle, and difficulty query parameters. It sends the key in the X-Api-Key header and uses a ten-second request timeout.
  4. The planner formats the name, muscle, and instructions for up to three valid records. An empty result leads to a fallback message.

A full_body request draws one muscle from the broadest pool. The code itself makes no guarantee of a balanced routine or training progression.

Dietitian and Spoonacular

  1. diet_tool(query) calls generate_meal_plan. That method invokes fetch_meal(diet=query), leaving time_frame at its default of day.
  2. fetch_meal calls /mealplanner/generate with timeFrame and apiKey. It sets diet for filtered plans such as vegetarian or vegan. Empty values and the string "None" omit that filter.
  3. For each returned meal, get_recipe_information calls /recipes/{id}/information. The planner formats the title, prep time, servings, ingredients, and recipe instructions when available.
  4. The planner appends calories in kcal and protein, fat, and carbohydrates in grams. A failed recipe lookup leaves the meal summary available. Missing meals produce a fallback message.

One diet tool invocation with n meals issues 1 + n sequential requests. The timeout applies to each call, so total response time can grow with meal count and additional model calls.

Chat and memory

What the user sees
st.session_state.messages holds the display transcript, including the greeting and any friendly error message. Streamlit renders this list on each rerun.
What the graph remembers
InMemorySaver stores graph checkpoints for a thread_id. Every new chat input submits one HumanMessage. The checkpointer recovers existing graph state for the same thread so the model can use earlier replies.
What survives a Streamlit rerun
@st.cache_resource keeps the compiled graph and its in-memory checkpointer available across reruns. The cached graph is shared across sessions within the process, so each session stores its own UUID to identify its graph thread. Without the decorator, each rerun would create a new graph with an empty checkpointer. A process restart clears checkpoint memory.
What the stream renders
main.py passes the data from each version 2 updates event to parse_langgraph_output. The parser skips supervisor updates and pairs worker text with the node name. Streamlit renders each reply as its worker completes.
# Shape of an illustrative update
{"dietitian": {"messages": [AIMessage(content="A meal plan", name="dietitian")]}}
# The parser returns
[("dietitian", "A meal plan")]

The supervisor graph and each ReAct worker cap execution at 15 graph steps. If either limit is hit or an error interrupts streaming, the UI logs the error type and displays a friendly error. Worker replies already displayed stay in the chat.

Design choices you can explain

These tradeoffs follow from the implementation. In an interview, tie your personal rationale to what you remember designing, changing, or testing.

Choice in the codeBenefit and cost
Central supervisorOne place makes routing and completion decisions. Workers can stay focused. Each handoff adds a model call, and routing quality depends on the supervisor's prompt and model.
Typed routing schemaA next field gives the application a predictable interface to the model. A valid destination can still be the wrong choice for the user's intent.
Separate specialist toolsFitness and dietitian see only their relevant tool, and the HTTP details live in tools.py. This limits each worker's tool surface and makes the HTTP behavior easier to exercise independently. The code still relies on the model to request the tool and use its result faithfully.
Direct wellness promptA short prompt-and-model chain is enough for the tips this worker provides. It relies on the model and the supplied conversation for its content.
Stream worker repliesThe user can read an early answer while later steps run and see which agent answered. Mixed requests may yield several separate replies because there is no final synthesis node.
In-memory checkpointsThe prototype gets follow-up context without a database. State is tied to the running process, which matters for restarts or a deployment with multiple processes.
Groq-backed modelHosted inference removes the requirement to run a model server locally. The tradeoff is a dependency on a provider key and network access. The earlier Ollama version ran against a local model service.

Fixes and limitations

The review notes record prior issues. The fixes below are visible in the current source.

Vegetarian input landed in the wrong parameter
fetch_meal(query) assigned the string to the first parameter, time_frame. The keyword call fetch_meal(diet=query) keeps the default timeframe and sends the requested diet filter.
Follow-up messages lost graph context
Recreating the graph also recreated its in-memory checkpointer. The cached graph keeps checkpoint state across script reruns. A per-session UUID replaces the earlier shared thread ID.
Wellness replies missed the user's context
The original prototype's prompt dropped the conversation. The current wellness node sends the system instructions and state["messages"] together.
The workout API always received stretching
The selected type was discarded in favor of a hard-coded value. The tool now passes the selected type as an argument.
HTTP failures could break the graph
The tools enforce a request timeout and validate responses before formatting them. The app shows a friendly error if graph execution fails.

The automated suite exercises the real graph with scripted model responses. It checks tool calls and results, multi-specialist turns, follow-up memory, session isolation, and malformed provider responses.

Run and explore

Use Python 3.11 or newer. From the repository root, install the pinned dependencies and run the offline tests. Create a .env from .env.example and fill in the keys before starting Streamlit.

python -m pip install -r requirements.txt
python -m unittest discover -s tests -v
streamlit run main.py
  • GROQ_API_KEY configures model access for the supervisor and all workers.
  • EXERCISE_API_KEY is used by the API Ninjas tool.
  • DIET_API_KEY is used by the Spoonacular tool.

main.py loads .env when the app starts. The prototype notebook uses Ollama and contains its own graph and exploratory calls.

  3. Failure handling. At fetch_exercises, trace what happens if a mocked response has a non-success status or a dictionary body. Explain each return value through generate_workout_plan and the worker.

Interview practice

A one-minute project walkthrough

I built a Streamlit chat app around a LangGraph supervisor. A message enters the graph, and the supervisor returns a structured decision to route it to fitness, dietitian, or mental wellness. Fitness and dietitian use ReAct workers that can call exercise and meal APIs. The wellness worker puts the conversation into a prompt and calls the model directly. Each worker returns a reply to the graph, which the UI displays as the step completes. The supervisor can continue routing or finish, and a per-session checkpoint thread gives the graph context for follow-up questions.

Adapt this to the work you personally did. Prepare one example you can explain in detail with the relevant file open, including what failed, how you checked it, and what changed.

Answer out loud, then reveal the explanation

What makes this a multi-agent project if the roles share one model?

The agents are distinct execution roles. Fitness and dietitian have different prompts and tools. Wellness has a direct prompt chain. The supervisor has a separate routing prompt and output schema. They share the model backend and exchange messages through graph state.

What exactly does the supervisor return?

The model call yields a structured next field. The Python node turns that into a Command that records the destination and moves the graph there. If the model chooses FINISH, the destination becomes END. Worker nodes produce the displayed text.

How does a ReAct worker use an API?

The model can ask to call the registered Python tool. The tool wrapper forwards the argument to a client in tools.py, the client requests the API and formats the data, and the model can use that tool return to compose its reply. The outer graph receives the worker's final message.

Why do you need both Streamlit state and LangGraph checkpointing?

Streamlit state is for the visible chat, including UI-only text. Graph checkpoints are for execution context that needs to be recovered on the next invocation. Caching preserves the checkpointer across reruns, while thread IDs keep sessions distinct within the process.

How did the vegetarian filter bug happen?

The first parameter of fetch_meal is time_frame, so passing "vegetarian" positionally filled the wrong field. Passing it as diet=query preserves the default timeframe and routes the value to the diet parameter.

What happens if the supervisor keeps calling the same agent?

It can repeat the worker because the prompt drives completion. The graph step limit bounds the loop and the UI error handler catches a failure. A future version could track requested topics and completion in explicit state.

How would you add another specialist?

Give the specialist its own node and a clear prompt. Bind a tool if its task needs one. Add its name to Route and the node mapping in create_agent_nodes, describe it in the supervisor prompt, and return control to the supervisor. Exercise routing and completion with sample prompts.

What would you test without live API keys?

Mock the model's routing decisions and HTTP responses. Check the route and termination, the exact meal and exercise request parameters, fallbacks for errors, and context across two turns using the same thread ID. CODE_REVIEW.md documents earlier mocked checks.
